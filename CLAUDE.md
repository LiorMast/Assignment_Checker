# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Automated grading of the Ruppin client-side (HTML/CSS) course exercises. Submissions are collected from the course Gmail mailbox, graded with Playwright against the rendered page, and turned into the course's grades workbook layout. Everything a student or grader sees (comments, feedback, reports) is in Hebrew; console output is in English.

## Commands

```bash
npm run fetch -- ex1                         # read the course mailbox, download group zips, write the submissions report
npm run fetch -- ex1 --since 2026-10-01 --deadline 2026-11-04   # override the schedule's dates
npm run fetch -- ex1 --no-label             # don't add the Gmail label (HW1-2026) to the exercise's mails
npm run grade -- ex1                         # grade everything in submissions/ex1/
npm run grade -- ex1 --group cgroup12        # re-grade one group (also --student <id>); other results are kept
npm run grade -- ex1 --workers=4             # extra args are passed through to Playwright
npm run grade -- ex1 --offline               # skip opening the mailed view links on proj.ruppin.ac.il
npm run calibrate -- ex1                     # compare results with hand grading in submissions/ex1/.manual.json
npm run report -- ex1                        # rewrite the reports from results.json + the hand edits, without grading
npm run selftest                             # self-tests: each exercise's solution + mutated copies (ex1 ~50, ex2 ~60)
npx playwright test --project=selftest -g "floats not cleared"   # one self-test case
npx tsc --noEmit                             # typecheck (there is no linter or build step; tsx runs TS directly)
```

After changing code, run `codegraph sync` so the CodeGraph index (`.codegraph/`) reflects the edits before the next `codegraph_explore` / `codegraph explore` query.

`npm run fetch` needs `GMAIL_USER` / `GMAIL_APP_PASSWORD` (a Google App Password) in `.env` (see `.env.example`); it uses IMAP, not the Gmail API.

## Pipeline

1. **Fetch** (`grader/fetch-mail.ts`, pure parsing in `grader/mail-parse.ts`): scans `[Gmail]/All Mail` for subjects containing `cgroupXX` (subjects are often non-standard; a mistyped prefix like `bgroup60` is corrected to `cgroup60` when the group is in the roster `groups.xlsx`, else in `exercises/groups.txt`; mails from roster students are read too), works out the exercise from the subject's `tarN` (else the link path) together with the mail date (`resolveExercise`: the claimed number is used if that exercise was already published at the mail's date, otherwise the date decides and a violation is recorded), keeps only each group's **latest** mail, downloads its zip from `proj.ruppin.ac.il` (falls back to an attached zip) to `submissions/<ex>/cgroupNN.zip`, and checks the mail against the submission procedure (`נוהל הגשת תרגילי בית.docx`). Writes `submissions/<ex>/.groups.json` (student IDs, links, assigned exercise number, violations, earlier mails), the mail text per group in `submissions/<ex>/.mail/cgroupNN.txt`, each zip extracted to `unzipped/<ex>/cgroupNN/` for checking by hand (`extractSubmission`; rebuilt on every fetch, not used by grading), and `results/<ex>/submissions.{html,xlsx}` (`grader/submissions-report.ts`).
   - Every mail assigned to the exercise (all of a group's mails, not only the latest) gets the Gmail label `HW<N>-<year>` (`HW1-2026`, `HW5a-2026`; `gmailLabel`: the year of the schedule's earliest publish date, so a semester shares one year) through IMAP `X-GM-LABELS`, created if missing (`labelMails`). A labelling failure is a warning, not an error; `--no-label` skips it.
   - Default `--since`/`--deadline` come from `exercises/schedule.md` (Markdown table parsed by `grader/schedule.ts`). The deadline is an exclusive cutoff: the whole due day counts (late from 00:00 of the next day, Israel time).
   - Parts of one exercise (`ex5a`/`ex5b`) share the number in mails; the mail date picks the part (`exerciseKeyFor`).
   - **The roster** `groups.xlsx` (project root, git-ignored, edited every semester; `grader/roster.ts`): groups with up to 3 students (name, ID, email), columns found by their Hebrew headers; the password column is never read. ExcelJS can't parse its table filter, so `loadRoster` strips `<autoFilter>` with jszip first. Without it, `exercises/groups.txt` lists the groups and students come from the mails.
   - Each mail's group is `assignGroup` (`mail-parse.ts`), first match wins: `manual-submissions/<ex>/mail-groups.json` (sender → group), **the group folder in the zip link** (then the view link; any letter before "group"), the sender's email in the roster, the mail's IDs when they all belong to one roster group, the subject. Disagreements are listed in the report (no deduction). Mails from roster senders without a group in the subject count only with a server link or a zip. A group's students are the roster's (`GroupRecord.students`); a student the subject leaves out is still graded, with no note. Zips and mail texts left from earlier runs for groups with no mail now are deleted (`removeStale`).
   - Students' links often contain spaces in folder names, so the mail client only makes part of the link clickable; `extractLinks` rebuilds these from the text and drops the cut-off part.
2. **Prepare** (`grader/prepare.ts`, called by `grader/cli.ts`): extracts every entry in `submissions/<ex>/` into `.work/<ex>/<id>/` (handles nested folders, zips inside zips, junk folders), finds the entry HTML, and writes `.work/<ex>/manifest.json`. The ID is `cgroupNN` when the name contains a group, otherwise an 8–9 digit student ID. Dot-files (like `.groups.json`) are skipped as submissions but read for group student IDs. Hand-added submissions in `manual-submissions/<ex>/cgroupNN/` (one zip per folder) replace that group's entry from `submissions/<ex>/` (`manualSubmissions`). A group's students come from the roster (else `.groups.json`). A group that submitted without a mail gets `manual-submissions/<ex>/cgroupNN/links.txt` with its two links (any text): fetch downloads the zip into that folder (`downloadLinkedZips`), and its links and live page are graded like a mail's; there is no subject to check (`SubmissionMail.subject` is undefined). IDs in a zip's file/folder names that belong to another roster group (`foreignGroups`) become `Submission.notes`, which `defineGradeSpec` turns into manual-review reasons.
3. **Grade**: the CLI spawns Playwright with `GRADER_EXERCISE=<ex>`. `exercises/<ex>/grade.spec.ts` is one call to `defineGradeSpec` (`grader/grade-spec.ts`), which generates **one test per manifest entry** and, after the exercise's rubric, runs the **submission-procedure checks** for every exercise (`grader/protocol.ts`: unrelated files, the mail's links from `Submission.mail` (not its subject), and the view link opened live on proj.ruppin.ac.il; resources that fail there but not locally cost points; a live page whose source differs from the zip's page (`textSimilarity` < 0.9) is a manual-review reason, since the zip may be an old version (not for hand-added `manual-submissions/` zips, which the grader chose); an unreachable server is a manual-review reason, `--offline` / `GRADER_OFFLINE=1` skips it). The course server ignores upper/lower case but refuses file names with `+`. The `site` fixture (`grader/fixtures.ts`) serves the folder with a local static server (`grader/server.ts`, which also detects path-case mismatches that would break on the real server) and takes a screenshot; `exercises/<ex>/checks.ts` runs the rubric through a `Grader` (`grader/grader.ts`).
4. **Report** (`grader/reporter.ts` → `grader/output.ts`): a custom Playwright reporter reads each test's `grader-result` attachment and writes `results/<ex>/grades.xlsx`, `summary.html`, `feedback/<id>.txt`, `results.json`, and with a roster **`students.xlsx`**: one row per roster student with the group's grade (`studentRows`; a group with no submission gets 0, "לא הוגש"; ungraded submissions get no grade, "לבדיקה ידנית"). Group results are expanded to **one xlsx row per student ID** (with a "קבוצה" column); a group with no IDs gets one row under its name and goes to manual review. `--student`/`--group` runs (`GRADER_PARTIAL=1`) merge into the previous `results.json`.
5. **Hand edits** (`grader/edits.ts`): `grades-viewer.html` (project root, one file, no libraries) imports `grades.xlsx` and lets the grader change comments, deductions, grades, manual-review reasons and the comments table, and mark groups as checked (`checked`: a status, not an edit, so it doesn't set `edited`). It saves `manual-submissions/<ex>/grade-edits.json` and `results/<ex>/grades.xlsx`. The edits are a layer: `writeOutputs` writes `results.json` from the automatic results and everything else after `applyEdits` (so calibration and partial re-grades see the script's own results); `npm run report -- <ex>` (`grader/report.ts`) rewrites the reports without grading. Hand-added comments are numbered from 201. `grades.xlsx` has a hidden `grader-data` sheet (automatic results, comments table, edits) that the page reads to keep editing. The page re-implements `applyEdits` and the workbook layout: when changing either, change both; the self-test "edits made in the page match the pipeline" compares them.

## Grading model (important when changing checks)

- Every student starts at 100 and loses points from the exercise's numbered comments table (`defineComments`). Tables are **versioned**: `exercises/<ex>/comments/vN.ts`, with `exercises/<ex>/comments.ts` re-exporting the active one and `COMMENTS_VERSION` (shown in grades.xlsx/summary). A version that grades were given with is frozen; changes go in a new version built as `{ ...V_prev.DEFS, overrides, new comments }`, so numbers (from **declaration order**) stay stable and new comments are appended. Log changes in `comments/CHANGELOG.md`.
- The submission-procedure comments are one shared table, `grader/protocol-comments.ts`, numbered **from 101** so they have the same number in every exercise; `exercises/registry.ts` (`defineExercise`) adds it to every exercise's comments. It is append-only like the exercise tables. Title/link rules are the pure `titleProblems` / `linkProblems` in `grader/mail-parse.ts`; the fetch report uses both, the grade only the links: **the mail subject is not graded** (comment 101 `SUBMIT_TITLE` is retired, 0 points, never given).
- `g.flag(comment, detail)` records a comment (never twice); deductions are soft-assertion failures, so a failed test is the normal outcome (the CLI treats exit code 1 as success).
- Errors inside `g.check(...)`, or a test that never reaches `g.complete()`, become **manual-review reasons, never deductions**. `g.review(..., { fatal: true })` means "could not be graded" (no grade).
- Checks inspect the rendered page (computed styles, positions) so that any valid technique passes; avoid source-text matching. The page is graded at 1920px; the last ex1 check re-measures the layout at 1366px (`atWidth`) for a 0-point note.
- Checks shared by exercises live in `grader/common-checks.ts` and take the calling exercise's comments (`checkInlineStyles(page, g, C)`), so each exercise flags its own numbers. ex1's rubric uses them; keep its behaviour identical (the ex1 self-tests assert exact comment sets).
- **ex2 (Bootstrap)**: `exercises/ex2/checks.ts` measures the page once per width in `WIDTHS` (400/650/850/1100/1920px, one per Bootstrap range) into snapshots, and the layout checks read those (cards per row and their width relative to the row's *content box*, versions area visible only from md, versions rows of two cells, six images in one row). Screenshots per width are attached to the report (`screenshot-<w>px`; only `screenshot` goes to summary.html). Regions are tagged `data-grader` (card, col, versions, popular-img...). Whether a working layout uses Bootstrap's classes is graded last (`NO_BOOTSTRAP` 8, `OWN_CSS_LAYOUT` 4, last year's comment 3); `BOOTSTRAP_CLASSES` is a 0-point note for classes from the PDF's table whose effect isn't already covered by a comment (`CLASS_COMMENTS`). A broken/missing Bootstrap link with Bootstrap classes in use is deducted once and the page is graded with Bootstrap added first (`injectBootstrap`). Kept ex1 design (e.g. `.page { max-width }` with container-fluid, padding on the cards' row) is not a deduction.
- `grader/bootstrap.ts`: Bootstrap 5.3.3 is a devDependency; `openSite` answers jsDelivr/unpkg/cdnjs requests for that version from `node_modules` (byte-identical, so SRI still matches). Other versions use the network; a network failure (not a 404) is a manual-review reason, never a deduction.
- When calibrating, also render each submission at a laptop width and compare its zip with the live page: both found differences the 1920px screenshot hides.
- To compare the script with hand grading: put the expected comment keys per submission in `submissions/<ex>/.manual.json` (student data, git-ignored), run `npm run grade -- <ex>` then `npm run calibrate -- <ex>` (`grader/calibrate.ts`, writes `results/<ex>/calibration.md` and a Hebrew `calibration.html` with the students' names from the roster). The notes in `.manual.json` are written in Hebrew, since they appear in that report. Every difference should end as a check fix or table change plus a self-test reproducing it.
- After changing checks or comments, run `npm run selftest`. `exercises/ex1/selftest.spec.ts` grades `exercise 1/ex1Solution` (expected 99: it has no header image) and mutated copies, each asserting its **exact** set of comments. `exercises/ex2/selftest.spec.ts` does the same for `exercise 2/ex2Solution` (a reference solution written from the PDF, expected 100) with the network blocked. The `grades-viewer.html` self-test can fail under parallel load (timing) and passes alone.

## Adding an exercise

Create `exercises/exN/` with `comments/v1.ts` + `comments.ts`, `checks.ts`, `grade.spec.ts` (one line: `defineGradeSpec('exN', gradeExN)`, which also adds the procedure checks), `selftest.spec.ts` (copy ex1), register it in `exercises/registry.ts` (title, sheet name and grade header match the course workbook), add a project to `playwright.config.ts`, and make sure it has a row in `exercises/schedule.md`.

## Data

`submissions/`, `manual-submissions/` (except its README), `unzipped/`, `.work/`, `results/`, `test-results/` and `.env` are git-ignored and contain student data. `exercise 1/` holds the official exercise PDF and solution; `exercise 2/` the PDF, the Bootstrap lecture, the reference solution, and last year's grades (git-ignored: student IDs); `assignment_grading.xlsx` is the course grades workbook whose layout `grades.xlsx` mirrors.
